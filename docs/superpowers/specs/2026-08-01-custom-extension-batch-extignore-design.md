# 커스텀 확장자 일괄 등록, extignore.txt, 정책 초기화 설계

## 목적

커스텀 확장자 등록을 단일 입력만 지원하던 기존 방식에 일괄 입력 모드를 추가하고, `extignore.txt` 파일 import/export와 확장자 정책 초기화 기능을 더한다. `docs/specs/REQUIREMENTS.md`, `PLANNING.md`, `DESIGN.md`는 UI/UX 개선 커밋과 분리하기 위해 일괄 입력 관련 내용이 제거된 상태이며, 이번 설계가 승인되면 세 문서에 반영한다.

## 범위

1. 커스텀 확장자 입력 모드 전환(단일/일괄)
2. 일괄 입력(쉼표 구분 텍스트)과 `extignore.txt` import(줄 단위)의 공통 처리 파이프라인
3. `extignore.txt` export(클라이언트 생성, 서버 API 없음)
4. 확장자 정책 초기화(커스텀 전체 삭제, 고정 전체 비활성화)
5. 20자 제한 정책을 "입력 전체 20자"에서 "항목별 20자"로 변경

## 1. 입력 모드 전환

- 커스텀 확장자 영역에 세그먼트 컨트롤(단일/일괄)을 추가한다.
- 전환 즉시 입력값을 초기화한다. 확인 대화상자는 표시하지 않는다.
- 단일 입력은 기존 동작(`maxlength=20`, `n/20`, Enter 또는 추가 버튼, 즉시 검증)을 그대로 유지한다.

## 2. 일괄 입력과 extignore.txt 처리

### 입력 형식

- 일괄 입력 텍스트: 쉼표로 구분한다(`exe,pdf,tar.gz`). 줄바꿈은 구분자로 인정하지 않는다.
- `extignore.txt` 파일: 줄 단위로 구분한다(`\n`, `\r\n` 지원, 빈 줄 허용). 주석(`#`)과 glob 패턴은 지원하지 않으며, 지원하지 않는 문법이 포함된 줄은 일반 형식 오류와 동일하게 처리한다(3-6절 참고).

### 공통 파이프라인

두 입력 방식은 구분자만 다르고 이후 처리는 동일한 파이프라인을 공유한다.

```text
원문
 → 분리(text: 쉼표 / file: 줄바꿈)
 → trim
 → 빈 값 제거
 → 항목별 normalize(lib/policy/normalize.ts의 normalizeExtensionInput 재사용)
 → 형식 검증(항목별 20자, 허용 문자, 연속 마침표 등 — 기존 단일 모드와 동일 기준)
 → 입력 내부 중복 제거
 → [서버] 기존 커스텀 중복 제외
 → [서버] 고정 확장자 자동 활성화 처리
 → [서버] 200개 제한 확인
 → [서버] 트랜잭션 반영
```

- 분리부터 형식 검증까지는 클라이언트에서 수행해 API 호출 없이 즉시 사용자에게 피드백을 준다. `lib/policy/normalize.ts`를 그대로 재사용하므로 단일 모드와 검증 기준이 항상 일치한다.
- 입력 내부 중복 제거 이후 단계(기존 커스텀 중복, 고정 확장자 자동 활성화, 200개 제한, 트랜잭션)는 클라이언트가 현재 정책 상태를 신뢰할 수 없으므로 서버에서만 최종 처리한다.

### 20자 제한 정책 변경

- 기존: 입력값 전체 길이가 20자 이하여야 한다.
- 변경: 일괄 입력과 `extignore.txt` import는 분리된 항목 각각이 20자 이하인지 검사한다. 단일 입력의 20자 제한은 그대로 유지된다(항목이 하나뿐이므로 기존과 동일하게 동작한다).
- 예: `exe,pdf,very-long-extension-name` → `exe`, `pdf`는 통과, `very-long-extension-name`은 초과. 하나라도 초과하면 전체 실패로 처리한다(2-4절).

### 중복 처리

- **입력 내부 중복**: `exe,exe,pdf` → `exe,pdf`로 정리한 뒤 처리한다.
- **기존 커스텀과의 중복**: 이미 등록된 커스텀 확장자와 겹치는 항목은 조용히 제외하고 나머지만 등록한다. 오류로 취급하지 않는다. 단일 모드는 동일 상황에서 오류로 거부하지만, 일괄 모드는 "대량 추가"가 목적이므로 하나가 겹친다고 전체를 막지 않는 쪽을 선택했다.
- **고정 확장자와의 중복**: 단일 모드와 동일한 정책을 적용한다. 비활성 상태면 자동 활성화하고, 이미 활성 상태면 변경하지 않는다. 두 경우 모두 커스텀 목록과 200개 제한에는 포함하지 않는다.
- **새 커스텀 0개**: 입력한 모든 항목이 기존 커스텀 중복이거나 고정 확장자 자동 활성화로만 처리되어 신규 커스텀이 0개여도 실패로 취급하지 않는다. 성공 처리하고 요약을 보여준다.

### 실패 정책

- 부분 저장은 없다. 다음 중 하나라도 발생하면 전체 실패하고 DB는 변경되지 않는다.
  - 형식 오류(정규화 실패, 항목당 20자 초과)
  - 처리 후 200개 초과
  - 서버 검증 실패, 트랜잭션 실패
- 형식 오류로 실패하면 문제 항목만 사유 구분 없이 하나의 목록으로 안내한다. 예: `올바르지 않은 항목이 있습니다: very-long-extension-name, 안녕, asdf-asdf`. 항목별로 어떤 규칙을 어겼는지는 구분해서 보여주지 않는다.
- `extignore.txt` import에 사용자가 직접 만든 임의 파일(주석이나 glob이 섞인 파일 등)을 올려 대량 형식 오류가 나더라도 위와 동일한 파이프라인으로 처리한다. 별도의 파일 내용 사전 안내나 방어 로직은 추가하지 않는다.

## 3. API

### `POST /api/policy/custom-extensions/batch`

- body: `{ "items": string[] }` (클라이언트에서 이미 분리, trim, 정규화, 형식 검증, 내부 중복 제거를 마친 값)
- 새 Postgres RPC `add_custom_extensions_batch(p_names text[])`를 추가한다. 기존 `add_custom_extension`(단일 등록)이 사용하는 advisory lock 키(`extension_policy_custom_add`)를 그대로 공유한다. 같은 키를 쓰지 않으면 단일 등록 요청과 배치 요청이 동시에 들어올 때 200개 제한이 깨질 수 있다.
- 하나의 plpgsql 함수 안에서 기존 커스텀 중복 제외, 고정 확장자 자동 활성화, 200개 제한 확인, 삽입을 모두 처리하고 하나의 트랜잭션으로 묶는다. 예외 발생 시 전체 롤백된다.
- 성공 응답에는 처리 요약을 포함한다: 신규 등록된 커스텀 목록, 자동 활성화된 고정 확장자 목록, 기존 커스텀 중복으로 제외된 개수.
- 형식 오류는 이 엔드포인트에 도달하기 전 클라이언트에서 차단하는 것이 기본 경로지만, 직접 API를 호출하는 경우에 대비해 서버도 각 항목을 다시 정규화하고 검증한다.

### `POST /api/policy/reset`

- 새 Postgres RPC `reset_extension_policy()`를 추가한다. 같은 advisory lock 아래에서 커스텀 확장자 전체 삭제와 고정 확장자 전체 비활성화를 한 트랜잭션으로 처리한다.
- 업로드 최대 크기 정책(`upload_settings`)은 초기화 대상에 포함하지 않는다. 이 기능은 확장자 정책만 초기화한다.

## 4. extignore.txt export

- 서버 API를 추가하지 않는다. 클라이언트가 이미 로드된 정책 상태(`usePolicy()`)로 파일을 직접 생성한다.
- 순서: 활성 고정 확장자(알파벳순) → 커스텀 확장자(알파벳순).
- `extignore.txt` 파일명으로 다운로드한다. (점(.)으로 시작하는 숨김 파일명 `.extignore`는 OS 파일 선택창과 `accept` 매칭 문제로 사용하지 않는다.)
- 가져오기 파일 선택의 `accept`는 `.txt,text/plain`이다.

## 5. 정책 초기화 UI

- 확장자 정책 영역에 초기화 버튼을 추가한다.
- 클릭 시 네이티브 `confirm()` 대화상자로 확인을 받는다.
- 고정 확장자 저장(debounce 대기 포함), 커스텀 확장자 추가/삭제 등 다른 영역의 요청이 진행 중이면 초기화 버튼을 비활성화한다. 진행 중인 작업과 초기화가 겹쳐 "초기화 직후 이전 작업이 다시 반영되는" 혼란을 막기 위함이다.
- 확인 후 `POST /api/policy/reset` 호출, 성공 시 `usePolicy().refetch()`로 전체 정책을 다시 조회해 화면을 갱신한다. 실패 시 화면 상태는 바꾸지 않고 토스트로 오류를 안내한다.

## 6. 프론트엔드 구성

### 컴포넌트

- `CustomExtensionModeToggle`: 단일/일괄 세그먼트 컨트롤
- `CustomExtensionBatchInput`: 일괄 입력 텍스트 영역, 등록 버튼, 플랫 목록 형태의 인라인 오류
- `ExtignoreControls`: 파일 선택(import) 버튼과 다운로드(export) 버튼. import는 파일을 선택하는 즉시 내용을 파싱하고 검증해 자동으로 제출한다. 일괄 입력 텍스트 영역에 내용을 채워 사용자가 확인하거나 수정하는 중간 단계는 두지 않는다. 형식 오류가 있으면 제출 없이 2-4절과 동일한 방식(플랫 목록)으로 바로 안내한다
- `ResetPolicyButton`: 초기화 버튼 + `confirm()` 처리 + 다른 영역 진행 여부에 따른 비활성화

### 훅

- `useCustomExtensionsBatch`: 입력 텍스트, 제출 중 상태, 실패 항목 목록을 관리. 클라이언트 사전 검증은 `lib/policy/normalize.ts`를 재사용
- `usePolicy`에 `resetPolicy()` 액션 추가

### 자동 활성화 결과 안내

- 배치로 여러 고정 확장자가 동시에 자동 활성화되어도(예: `exe`, `bat` 동시 입력) 개별 항목으로 포커스를 이동하지 않는다. "exe, bat 활성화됨, pdf 1개 등록됨"처럼 요약을 토스트나 결과 메시지로만 안내한다. 단일 모드의 "해당 항목으로 포커스 이동" 원칙은 일괄 처리에는 적용하지 않는다.

## 7. 테스트 전략

- **순수 함수**: 쉼표/줄바꿈 분리, trim, 빈 값 제거, 입력 내부 중복 제거 로직을 단위 테스트로 검증한다.
- **API 통합 테스트**
  - 단일 등록 요청과 배치 요청이 동시에 200개 한도에 걸치는 상황에서 최종 개수가 200을 넘지 않는지(같은 advisory lock 키 공유 검증)
  - 배치 중 일부 항목이 형식 오류일 때 전체가 롤백되고 DB에 아무 변경도 없는지
  - 기존 커스텀과 겹치는 항목이 조용히 제외되고 나머지만 등록되는지
  - 모든 항목이 기존 커스텀 중복이거나 고정 확장자 자동 활성화로만 처리되어 신규 커스텀이 0개일 때 성공 처리되는지
  - `POST /api/policy/reset`이 커스텀 전체 삭제와 고정 전체 비활성화를 트랜잭션으로 처리하고, 업로드 크기 정책은 그대로 유지하는지
- **훅/컴포넌트 테스트**
  - 모드 전환 시 입력값이 초기화되는지
  - 다른 영역이 진행 중일 때 초기화 버튼이 비활성화되는지
  - 배치 실패 시 플랫 목록 형태로 문제 항목이 표시되는지
