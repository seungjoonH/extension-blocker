# UI/UX 개선 설계 (1차)

## 목적

실제 화면을 사용해보며 발견한 불편사항을 `docs/specs/REQUIREMENTS.md`, `docs/specs/PLANNING.md`와 대조해 반영한다. `CONSIDERATIONS.md` 작성은 이번 설계 범위에서 제외하고 별도 작업으로 진행한다.

## 범위

이번 설계에서 다루는 항목은 다음 세 가지다.

1. 레이아웃 재구성
2. 커스텀 확장자 Enter 키 추가 지원
3. 검증 오류 텍스트로 인한 CLS(레이아웃 시프트) 방지

다음 항목은 이번 설계에 포함하지 않는다.

- 커스텀 확장자 삭제 버튼 `X` → `x` 표기: 이미 반영되어 있어 추가 작업이 필요 없다
- 업로드된 파일 목록: `REQUIREMENTS.md`(원본 파일명 저장), `PLANNING.md`(권한 또는 접근 제한 상태)에 이미 근거와 함께 "전체 파일 목록은 공개하지 않는다"고 결정되어 있다. 이번에는 이 결정을 유지하고 코드를 변경하지 않는다. 반영 여부 확인은 이후 `CONSIDERATIONS.md` 작업에서 다룬다
- 확장자 차단 여부의 클라이언트 사전 검증: 추가하지 않는다. `PLANNING.md` 8절의 기존 설계(확장자 검증은 서버 전용)를 그대로 유지한다

## 1. 레이아웃 재구성

### 배경

현재 화면 순서는 고정 확장자 → 커스텀 확장자 → 업로드 크기 정책 → 파일 업로드다. 커스텀 확장자 등록 개수가 늘어날수록 목록이 길어지고, 그 아래에 있는 업로드 크기 정책 섹션이 계속 밀려나 사용성이 떨어진다.

### 새 구조

```text
[업로드 크기 정책 섹션]          ← 맨 위, 독립 섹션

[확장자 섹션]                    ← 하나의 큰 섹션(제목 하나)
  - 커스텀 확장자 입력 필드 + 추가 버튼   ← 맨 위
  - 고정 확장자 체크박스 목록            ← 중간
  - 커스텀 확장자 등록 목록(삭제 버튼들)  ← 맨 아래

[파일 업로드 섹션]                ← 그대로 유지
[전역 알림 영역]                  ← 토스트, 위치 무관(화면 전역 고정)
```

커스텀 확장자 목록이 늘어나도 그 아래에 다른 섹션이 없으므로 더 이상 다른 영역을 밀지 않는다.

### 컴포넌트 변경

- `CustomExtensionsSection`을 입력부(입력 필드 + 글자 수 + 추가 버튼 + 인라인 오류)와 목록부(등록 개수 표시 + 목록 + 삭제 버튼)로 분리한다.
- 상태(`list`, `input`, `isSubmitting`, `inlineError`, `deletingIds` 등)는 상위 조합 컴포넌트(현재 다섯 섹션을 조합하는 페이지 컴포넌트)에서 훅으로 관리하고, 입력부·목록부·`FixedExtensionsSection`에 props로 내려준다. 입력부와 목록부를 완전히 독립된 컴포넌트로 만들되 상태는 공유해야 순서를 자유롭게 바꿀 수 있다.
- `FixedExtensionsSection`은 내부 로직 변경 없이 위치만 옮긴다.
- `UploadSizeSection`은 내부 로직 변경 없이 위치만 옮긴다.

### 문서 반영

`docs/specs/PLANNING.md` 4절(화면 목록과 목적), 5절(영역별 구성 요소와 사용자 행동)을 새 구조에 맞게 갱신한다. 다섯 영역이라는 개수 표현과 영역별 순서 설명을 실제 배치와 일치시킨다.

## 2. 커스텀 확장자 Enter 키 추가 지원

### 배경

`docs/specs/REQUIREMENTS.md`의 "제한 초과 시 UX" 항목에 "Enter 키 제출도 동일한 조건으로 제한"이 이미 명시되어 있다. 그러나 현재 `CustomExtensionsSection.tsx`에는 `<form>`도 `onKeyDown` 핸들러도 없어 Enter 키로 추가할 수 없다. 이는 이미 확정된 요구사항과 구현이 어긋난 결함이다.

### 처리 방식

입력 필드를 `<form onSubmit>`으로 감싸거나 입력 필드에 `onKeyDown`으로 Enter 키를 감지해 `handleAdd`를 호출한다. 기존 `canSubmit` 조건(빈 값, 제출 중, 200개 초과)을 그대로 적용해 버튼 클릭과 동일한 제약을 받는다.

### 문서 반영

`docs/specs/REQUIREMENTS.md`에는 이미 근거가 있으므로 별도 갱신이 필요 없다. `docs/specs/PLANNING.md` 5.2절에는 Enter 제출이 명시적으로 언급되어 있지 않으므로, 레이아웃 갱신과 함께 한 줄 보완한다.

## 3. 검증 오류 텍스트 CLS 방지

### 배경

`CustomExtensionsSection`의 인라인 오류(`inlineError`)와 정원 초과 안내(`limitReached`)는 조건에 따라 나타나거나 사라지는 `<p>` 요소로, 등장 시 그 아래 목록이 아래로 밀리는 레이아웃 시프트(CLS)가 발생한다.

### 처리 방식

오류 표시 영역에 한 줄 분량의 최소 높이를 항상 예약해, 오류 문구가 나타나거나 사라져도 그 아래 요소의 위치가 바뀌지 않게 한다.

### 적용 범위

`CustomExtensionsSection`의 인라인 오류와 정원 초과 안내에 적용한다. `FileUploadSection`의 `filenameError`, 업로드 결과 표시는 화면 하단에 위치해 밀림 영향이 상대적으로 적으므로, 이번 설계에서는 우선순위를 낮게 두고 구현 중 실제 영향을 확인해 필요 시에만 동일하게 적용한다.

## 테스트

- 컴포넌트 분리에 맞춰 `components/CustomExtensionsSection.test.tsx`, `components/FixedExtensionsSection.test.tsx`를 갱신한다.
- Enter 키로 추가되는 동작과 기존 `canSubmit` 제약이 Enter 제출에도 동일하게 적용되는지 테스트 케이스를 추가한다.
- 레이아웃 순서와 CLS 방지는 시각적 요소이므로 자동화 테스트로 완전히 검증하기 어렵다. 컴포넌트 구조(어떤 섹션이 어떤 부모 아래 렌더링되는지)는 테스트로 확인하고, 실제 시각 확인은 구현 후 브라우저로 점검한다.
