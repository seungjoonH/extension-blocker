# Prompt Log

AI 활용 과정과 사용자의 판단을 작업 단위로 기록한다.
기록은 작업 순서에 따라 시간 오름차순으로 배치한다.

## 공통 AI 도구

- **Claude Code**: 프로젝트의 AI 워크플로 구성, 문서 작성, 코드 수정, 검증과 기록을 수행하는 주 Agent로 사용. Skills, MCP, 프로젝트 규칙과 플러그인을 하나의 실행 환경에서 연결하고, 정의한 작업 흐름을 반복 적용하기 위해 선택함
- **Superpowers**: 기획, 계획 작성, TDD, 체계적 디버깅과 완료 전 검증 절차를 실제 작업 단계에 적용하기 위해 사용. AI가 바로 구현에 들어가지 않고 일정한 개발 절차를 따르도록 구성함
- **Context7**: 라이브러리의 최신 API와 설정을 공식 문서 기준으로 확인하기 위해 사용. AI의 기존 지식이나 버전 차이로 발생할 수 있는 오류와 추측을 줄이기 위해 MCP로 연결함
- **document-review**: Markdown 문서의 문체, 형식, 용어와 프로젝트 상태의 정합성을 일관되게 검토하기 위해 만든 프로젝트 전용 스킬
- **prompt-log**: 핵심 프롬프트, AI 활용 과정과 사용자 판단을 작업 단위로 기록하고 누락을 방지하기 위해 만든 프로젝트 전용 스킬. AI는 사용자의 회고를 대신 작성하지 않고 질문과 판단 대상을 제공하도록 제한함
- **commit-commands**: 검증이 끝난 변경사항을 논리적인 작업 단위로 검토하고 커밋하기 위해 사용. 커밋 전 변경 범위와 메시지를 확인하는 절차에 적용함

## 001. AI 개발 워크플로 구성

### 작업 요약

```
prompt-log를 사용해서 이번 AI 개발 워크플로 구성 작업의 로그 초안을 생성해줘. [...] 작업 내역과 AI 활용 항목만 채우고, 나의 판단과 회고 항목은 비워둔 채로 남겨줘.
```

**요청 의도**

> AI 활용 과정과 작업 결과는 자동으로 정리하되, 사용자의 판단과 회고는 실제 작업을 진행한 제가 직접 작성해야 한다고 생각했습니다. 따라서 AI가 회고 내용을 대신 작성하지 않고 작성 영역만 남기도록 요청했습니다.

#### 4. 프롬프트 기록 추가 요청

```
prompt-log 스킬의 프롬프트 기록 방식과 현재 docs/ai/PROMPT_LOG.md의 001번 로그를 수정하는데, AI에 입력한 핵심 프롬프트를 기록하되 로그가 지나치게 길어지지 않도록 가독성과 선별 기준을 강화해줘.
```

**요청 의도**

> 과제에서 AI에 입력한 프롬프트와 재질문 과정을 기록하도록 요구하고 있어, 작업의 흐름에 영향을 준 핵심 프롬프트를 남길 필요가 있다고 생각했습니다. 다만 모든 대화를 기록하면 로그가 지나치게 길어질 수 있어, 핵심 프롬프트만 선별하고 접이식으로 구성해 가독성을 유지하기 위해 요청했습니다.

### AI 활용 과정

- Superpowers, Context7, commit-commands의 실제 설치와 인식 상태를 점검해 중복 등록과 설치 오류를 정리함
- `prompt-log`가 사용자의 판단과 회고를 대신 작성하지 않도록 역할을 제한하는 정책을 AI가 제안해 반영함
- `AI_WORKFLOW.md`, `CLAUDE.md`, 각 `SKILL.md` 간 설명 불일치를 AI가 점검해 제시하고 수정함

### 최종 반영

- `docs/ai/AI_WORKFLOW.md` 작성 및 `document-review`, `prompt-log` 프로젝트 스킬 구성
- `prompt-log`가 사용자 판단을 대신 작성하지 않도록 정책 확정
- Superpowers, Context7, commit-commands 중복 등록과 설치 오류 정리
- 문서 간 설명 불일치 수정 및 `.gitignore`에 `.claude/settings.local.json` 추가

### 나의 판단과 회고

#### AI의 제안 중 그대로 반영한 내용은 무엇인가?

이번 작업에서는 다음 제안이 실제 반영 후보에 포함되었습니다.

- 기능 구현 전에 `AI_WORKFLOW.md`를 먼저 작성하는 방식
- `document-review`와 `prompt-log`를 프로젝트 전용 스킬로 분리하는 방식

> 기능 구현 전에 AI 활용 방식과 작업 절차를 먼저 정의하는 제안을 반영했습니다. 구현 후 활용 과정을 복기하면 실제 판단이나 수정 과정이 누락될 수 있다고 생각했습니다. 또한 문서 검토와 AI 활용 기록의 역할이 다르므로 `document-review`와 `prompt-log`를 각각 분리해 구성했습니다.

#### AI의 제안을 수정해서 반영한 내용은 무엇인가?

이번 작업에서는 다음 항목을 여러 차례 수정했습니다.

- `prompt-log`의 로그 구조와 분량
- 고정된 회고 항목을 작업 맥락에 맞는 질문으로 변경
- 유도성 있는 회고 질문을 중립적인 질문으로 변경
- 모든 프롬프트가 아닌 핵심 프롬프트만 기록하도록 범위 제한

> 초기 `prompt-log`에는 실제 입력 프롬프트가 포함되지 않았고, 회고 질문에 사용자의 판단 근거가 미리 들어가 있었습니다. 이를 직접 확인한 뒤 핵심 프롬프트와 요청 의도를 기록하도록 보완하고, 작업 맥락에 맞는 중립적인 회고 질문을 제공하도록 수정했습니다. 또한 로그가 길어지지 않도록 핵심 프롬프트만 접이식으로 기록하도록 변경했습니다.

#### AI의 제안 중 제외한 내용은 무엇인가?

이번 작업에서는 다음 제안이나 작성 방식의 제외 여부를 판단했습니다.

- AI가 사용자의 판단과 회고 답변까지 대신 작성하는 방식
- 작업 결과에 영향을 주지 않은 모든 대화를 프롬프트 로그에 기록하는 방식
- 도구 선택 이유와 AI 결과 판단을 하나의 회고 영역에 함께 작성하는 방식

> AI가 사용자의 판단과 회고까지 작성하는 방식은 제외했습니다. 회고에는 실제 사용자의 선택과 근거가 들어가야 한다고 생각했기 때문입니다. 또한 모든 대화를 기록하면 핵심 판단 과정이 묻힐 수 있어 제외했으며, 도구 선택 이유는 공통 AI 도구 영역으로 분리하고 회고는 AI 결과를 채택, 수정, 제외한 판단에만 집중하도록 정리했습니다.

## 002. 파일 업로드 요구사항 문서화

### 작업 요약

과제 원문을 기준으로 `docs/specs/REQUIREMENTS.md`를 작성하고, 필수 요구사항과 구현 범위와 의사결정, 추가 고려사항, 검증 체크리스트 네 단계로 문서를 구성했다. 결정 필요로 남은 24개 항목을 사용자와 하나씩 논의해 확정하고, document-review로 문서 품질을 검증해 발견된 문제를 수정했다. 이후 유일하게 남아 있던 미확정 항목인 업로드 파일명의 구체적인 최대 길이를 논의해 확정하고 검증 체크리스트를 닫았다.

### 프롬프트 기록

<details>
<summary>프롬프트 보기</summary>

#### 1. 최초 요청

```
과제 원문을 기준으로 요구사항을 분석해서 docs/specs/REQUIREMENTS.md에 작성해줘. 문서는 다음 순서로 구성하는데, [...] 아직 판단하지 않은 항목은 임의로 결정하지 말고 결정 필요로 표시해줘.
```

**요청 의도**

> 과제 원문의 필수 요구사항과 추가 고려사항을 빠짐없이 구조화하되, 아직 논의하지 않은 내용을 AI가 임의로 확정하지 않도록 요청했습니다. 구현 전에 요구사항과 결정이 필요한 쟁점을 분리해 이후 논의의 기준이 되는 문서를 만들고자 했습니다.

#### 2. 논의 진행 방식 지시

```
docs/specs/REQUIREMENTS.md의 결정 필요로 남아 있는 항목을 사용자와 하나씩 논의해 구체화해줘. [...] 한 번에 여러 항목을 결정하지 말아줘.
```

**요청 의도**

> 여러 쟁점을 한꺼번에 결정하면 각 선택의 근거와 영향이 섞일 수 있으므로, 항목별 의미와 선택지를 확인한 뒤 하나씩 결정하고자 했습니다. 논의 과정에서는 세부 항목별로 기존 요구사항을 구체화하거나 수정하고, 과제의 본질과 관련이 없거나 다른 항목과 중복되는 내용은 삭제했습니다. 각 과정에서 이루어진 사용자의 구체적인 판단과 변경 근거는 나의 판단과 회고에 통합해 정리했습니다.

#### 3. 품질 검토 요청

```
기존 AI workflow에 따라 현재 요구사항 문서의 품질을 검토해줘. 다음 항목만 확인해줘. [...] 문제가 발견되면 임의로 수정하지 말고, 문제 위치와 이유, 수정 방향만 정리해줘.
```

**요청 의도**

> 모든 논의가 끝난 뒤 문서의 결정 내용이 서로 일관되는지, 질문과 답변이 같은 쟁점을 다루는지, 중복이나 삭제 흔적이 남아 있지 않은지를 커밋 전에 확인하고자 했습니다. AI가 확정된 내용을 임의로 변경하지 않도록 문제점과 수정 방향만 먼저 보고하도록 요청했습니다.

#### 4. 파일명 길이 확정 요청

```
파일명 길이 제한은 데이터베이스나 프레임워크에 따라 정하는 구현 방식이 아니라 사용자가 업로드할 수 있는 입력 범위를 정하는 정책이고, 기술 설계로 넘기면 요구사항 문서와 체크리스트가 미완성 상태로 남으니까, 요구사항 단계에서 255자로 확정해줘. [...]
```

**요청 의도**

> 파일명 길이 제한은 구현 방식이 아니라 사용자 입력 범위를 정하는 정책이므로 기술 설계 단계로 미루지 않고 요구사항 단계에서 확정해야, 요구사항 문서와 검증 체크리스트가 완결된 상태로 남는다고 판단해 요청했습니다.

</details>

### AI 활용 과정

- 4단계 구조에 맞춰 문서를 작성하면서, 과제 원문 대비 누락된 세부 요구사항(입력 길이 제한, 고정 확장자 미표시 규칙, 원본 파일명 위험 등)을 AI가 점검해 추가함
- 결정 필요 24개 항목마다 의미, 선택지, 장단점과 권장안을 제시하고 사용자의 결정을 반영, 이미 다른 항목에서 결정된 내용과 겹치는 경우(정책 변경 로그, 연속된 마침표, 동일 파일 재업로드)는 새로 논의하지 않고 기존 항목을 참조하도록 안내함
- 사용자가 과제 범위를 벗어난다고 판단해 삭제를 요청한 항목(사용자별 정책 확장, 화이트리스트 전환, 동일 파일 재업로드)을 문서와 논의 번호에서 제거함
- document-review로 7개 기준(일관성, 질문과 결정의 일치, 중복, 카테고리 배치, 재논의 여부, 삭제 흔적, 체크리스트 반영)을 검토해 체크리스트 누락 1건과 용어 불일치 1건을 발견해 보고함
- 품질 검토 이후 유일하게 남아 있던 미확정 항목(업로드 파일명 길이 제한의 구체적인 수치)을 확인해 보고하고, 사용자가 제시한 255자 제한과 서버 최종 검증, 클라이언트 사전 안내, 원본 파일명의 메타데이터 저장, 오류 메시지 제공 방침을 적용 방향에 반영함

### 최종 반영

- `docs/specs/REQUIREMENTS.md`를 필수 요구사항, 구현 범위와 의사결정, 추가 고려사항, 검증 체크리스트 4단계 구조로 작성
- 검증과 보안, 정책과 데이터, UX와 예외, 운영과 확장 하위 24개 항목을 사용자와 개별 논의해 결정하고 적용 방향, 판단 이유, 예시를 반영
- 결정하지 않기로 한 3개 항목(사용자별 정책 확장, 화이트리스트 전환, 동일 파일 재업로드)을 문서에서 삭제
- document-review로 발견한 검증 체크리스트 누락(업로드 파일명 길이 제한 항목)과 용어 불일치(`Storage`를 `저장소`, `저장 식별자`로 통일)를 수정
- `업로드 파일명 길이 제한` 항목에 최대 255자 제한과 판단 이유 반영, 검증 체크리스트를 `업로드 파일의 원본 파일명이 확장자를 포함해 255자를 초과하면 서버에서 거부됩니다`로 확정

### 나의 판단과 회고

#### AI의 제안 중 그대로 반영한 내용은 무엇인가?

이번 작업에서는 다음 논의에서 AI가 제시한 권장안을 그대로 선택했습니다.

- 서버 사이드 검증, 대소문자 정규화, 확장자 없는 파일 처리의 기본 방향
- 빈 입력 처리, 연속된 마침표 처리, 반응형 레이아웃 방식

> 클라이언트 검증만으로는 요청 변조나 직접적인 API 호출을 막을 수 없으므로, 서버가 현재 정책을 기준으로 최종 검증해야 한다는 제안을 그대로 반영했습니다. 또한 대소문자 차이와 선행 마침표처럼 의미가 동일한 입력은 정규화하고, 빈 입력이나 연속된 마침표처럼 의미가 불분명한 값은 명확하게 거부하는 방식이 일관적이라고 판단했습니다. 반응형은 복잡한 브레이크포인트를 구성하기보다 단순한 화면 구조에 맞춰 요소가 자연스럽게 줄바꿈되도록 하는 방향을 선택했습니다.

#### AI의 제안을 수정해서 반영한 내용은 무엇인가?

이번 작업에서는 다음 논의에서 AI가 제시한 선택지를 조합하거나 세부 조건을 바꿔 반영했습니다.

- 확장자 없는 파일과 숨김 파일 처리(숨김 파일 예외를 없애고 접미사 규칙으로 통일)
- 저장 실패 처리(고정 확장자는 낙관적 업데이트, 커스텀 확장자는 서버 응답 후 반영으로 유형별 분리)
- 파일 시그니처 검증(매직 넘버 직접 관리 대신 ClamAV 기반 보안 필터로 재구성)

> 숨김 파일을 항상 확장자가 없는 파일로 처리하면 env 정책으로 .env를 차단하려는 사용자의 기대와 어긋날 수 있다고 생각했습니다. 따라서 일반 파일과 숨김 파일을 별도로 구분하지 않고 점 경계를 포함한 접미사 규칙으로 통일했습니다. 저장 방식은 모든 변경에 하나의 전략을 적용하기보다, 연속 조작 가능성이 있는 고정 확장자에는 낙관적 업데이트와 Debounce를 적용하고 커스텀 확장자의 추가와 삭제에는 서버 저장 결과를 기준으로 반영하도록 나누었습니다. 파일 보안 검사는 애플리케이션에서 매직 넘버 목록을 직접 관리하는 방식보다 확장자 정책과 ClamAV 검사를 독립된 필터로 구성하는 것이 역할과 책임을 명확히 할 수 있다고 판단했습니다.

#### AI의 제안 중 제외한 내용은 무엇인가?

이번 작업에서는 다음 논의에서 AI가 제시한 선택지 대신 다른 방향을 선택하거나 항목 자체를 제외했습니다.

- 고정 확장자와 커스텀 확장자 중복 처리(AI가 권장한 등록 거부 대신 자동 활성화 방식 선택)
- 사용자별 정책 확장, 화이트리스트 전환, 동일 파일 재업로드 항목 자체를 논의 없이 삭제

> 사용자가 커스텀 입력란에 고정 확장자를 입력한 경우에는 단순히 오류로 거부하기보다 해당 고정 확장자를 활성화하는 것이 사용자의 차단 의도를 더 직접적으로 반영할 수 있다고 판단했습니다. 사용자별 정책과 화이트리스트 전환은 현재 과제에서 요구하지 않는 미래 확장에 대한 논의이므로 문서의 핵심을 흐릴 수 있어 삭제했습니다. 동일 파일 재업로드는 원본 파일명 저장 항목에서 독립 저장과 덮어쓰기 금지 원칙이 이미 확정되어 있어 별도 논의로 유지할 필요가 없다고 판단했습니다.

> 정책 관리와 파일 업로드는 서로 다른 역할을 가지지만, 정책을 변경한 직후 실제 업로드 결과를 확인하는 흐름이 핵심이라고 생각했습니다. 따라서 별도 화면으로 나누기보다 한 페이지 안에서 영역만 명확히 구분하는 방식을 선택했습니다. 파일 업로드는 필수 기능에 집중하기 위해 클릭 선택만 지원하고, 진행률을 정확히 계산할 필요가 없으므로 스피너와 상태 텍스트로 처리했습니다. 커스텀 확장자 삭제는 복구하기 어려운 데이터가 아니고 다시 등록할 수 있으므로 별도의 확인 절차 없이 즉시 처리하는 것이 적절하다고 판단했습니다.

#### AI의 제안을 수정해서 반영한 내용은 무엇인가?

이번 작업에서는 다음 논의에서 AI가 제시한 선택지를 조합하거나 세부 조건을 바꿔 반영했습니다.

- 알림 패턴(토스트와 인라인 구분을 AI의 일반적인 권장안보다 메시지 성격별로 세밀하게 직접 지정)
- 업로드 결과 표시(누적 이력 대신 직전 시도 1건만 표시, 동일 파일 재시도도 새 시도로 처리)
- 서버 검증 순서(파일명, 확장자, 크기, ClamAV, 저장 순서를 직접 확정)
- 여러 차례의 정합성 검토에서 발견된 모순과 공백(빈 상태와 업로드 성공 상태의 충돌, 파일명 검증에서 빈 파일명과 길이 초과의 클라이언트/서버 구분, 파일 하나만 선택 가능하다는 명시 누락 등)을 보완
- 저장 대기 중 페이지 이탈 방지 방식(`beforeunload` 확인 대화상자로 확정)

> 알림은 메시지 성격에 따라 토스트와 인라인으로 구분했습니다. 저장 결과처럼 일시적인 피드백은 토스트로 제공하고, 입력 오류와 업로드 차단 사유처럼 사용자가 확인하거나 수정해야 하는 정보는 관련 영역에 유지했습니다. 업로드 결과는 이력처럼 누적하지 않고 최근 시도 1건만 표시했으며, 동일 파일 재시도도 새로운 업로드 시도로 처리했습니다. 서버 검증은 파일명, 확장자, 크기, ClamAV 순으로 구성하고, 문서 검토에서 발견된 상태 충돌과 누락을 요구사항 기준으로 보완했습니다. 저장 대기 중 이탈은 변경사항 유실을 막기 위해 브라우저 기본 확인 대화상자를 사용하기로 결정했습니다.

#### AI의 제안 중 제외한 내용은 무엇인가?

이번 작업에서는 다음 선택지를 검토했지만 채택하지 않았습니다.

- 정책 관리와 업로드를 별도 화면으로 분리하는 안
- 드래그앤드롭 업로드 지원
- 모든 메시지를 토스트로 통일하는 안
- 저장 대기 중 이탈 시 조용히 저장을 시도(flush)하는 방식

> 정책 관리와 업로드를 별도 화면으로 분리하면 화면 책임은 명확해지지만, 정책 변경 후 적용 결과를 확인하기 위해 이동해야 하므로 핵심 사용자 흐름이 끊긴다고 판단했습니다. 드래그앤드롭은 사용성을 높일 수 있지만 클릭 선택만으로 필수 기능을 충분히 제공할 수 있어 범위에서 제외했습니다. 모든 메시지를 토스트로 처리하면 입력 오류나 업로드 차단 사유가 자동으로 사라질 수 있으므로 채택하지 않았습니다. 페이지 이탈 시 저장을 자동으로 시도하는 방식도 네트워크 오류가 발생하면 사용자가 유실 사실을 확인하기 어려워 제외했습니다.

### AI 활용 과정

- subagent-driven-development로 태스크마다 신선한 구현 서브에이전트를 디스패치하고, 완료 후 별도의 리뷰 서브에이전트가 스펙 준수(요구사항 대비 누락/과잉/오해)와 코드 품질(관심사 분리, 오류 처리, 테스트 품질)을 검토하는 루프를 26회 반복함
- 리뷰에서 Critical/Important 결함이 발견되면 수정 라운드를 거쳐 스코프를 좁힌 재검토로 해결 여부를 확인하고, Minor 결함은 워크스페이스 원장(progress.md)에 기록해 이후 최종 리뷰가 참고하도록 함
- 계획 문서의 참고 코드와 PLANNING.md 사이에 간극(토스트 규칙, beforeunload, 포커스 관리, validateFilename 미사용)을 여러 차례 발견해 AskUserQuestion으로 사용자에게 보고하고, 계획 자체를 먼저 보완한 뒤에만 태스크를 디스패치함
- 태스크 리뷰에서 발견된 결함 중 명백한 버그(동시 저장 경쟁 상태, 재동기화 시 다른 항목 덮어쓰기, 잘못된 오류 매핑, 로깅 누락)는 AI가 직접 수정하고, 값이 정의되지 않았거나 범위 판단이 필요한 사안(업로드 타임아웃 시간, 접근성/반응형 CSS 포함 여부)은 사용자에게 확인 후 반영함
- 26개 태스크 완료 후 가장 성능이 높은 모델로 전체 브랜치(49커밋, 82개 파일) 리뷰를 별도로 디스패치해, 보안(ClamAV 판정 불명확 상태 처리), 동시성, 컴포넌트 간 통합, 로깅 완전성 등 태스크 단위 리뷰로는 확인할 수 없는 교차 관심사를 점검함
- 최종 리뷰에서 발견된 결함을 백엔드/보안과 프런트엔드/접근성 두 라운드로 나눠 순차 수정하고, 전체 수정 범위를 다시 스코프드 리뷰로 검증함(실제 Chrome을 좁은 뷰포트로 구동해 반응형 동작을 직접 확인)
