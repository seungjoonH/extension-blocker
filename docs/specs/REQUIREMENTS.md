# Requirements

`docs/과제_파일업로드_AI개발.md`를 기준으로 요구사항을 분석합니다.  
아직 판단하지 않은 항목은 임의로 결정하지 않고 `결정 필요`로 표시합니다.

## 1. 필수 요구사항

과제에서 반드시 구현해야 하는 범위입니다.

### 확장자 차단 정책 관리

#### 고정 확장자

- `bat`, `cmd`, `com`, `cpl`, `exe`, `scr`, `js` 제공
- 기본 상태는 모두 선택 해제
- 선택 상태를 DB에 저장
- 새로고침 후에도 저장 상태 유지
- 커스텀 확장자 목록에는 표시하지 않음

#### 커스텀 확장자

- 최대 20자 입력
- 추가 시 DB 저장 후 목록 표시
- 최대 200개 등록
- 등록 항목 삭제
- 중복 등록 방지

### 파일 업로드

- 실제 파일 업로드 기능 제공
- 현재 차단 정책을 실제 업로드에 적용
- 차단 파일은 명확한 사유와 함께 거부
- 허용 파일은 업로드 성공 처리
- 서버에서 차단 정책 검증

## 2. 구현 범위와 의사결정

과제 3장의 고려사항별 구현 여부, 적용 방향과 판단 이유를 기록합니다.

### 검증과 보안

#### 서버 사이드 검증

- 결정: 구현
- 적용 방향:
  - 모든 파일 업로드 요청에서 서버가 현재 차단 정책을 조회
  - 파일 저장 전에 차단 여부 검증
  - 클라이언트 검증 결과와 관계없이 서버 검증 수행
- 판단 이유:

  > 클라이언트 검증은 직접 API를 호출하거나 요청을 변조하여 우회할 수 있습니다. 차단 정책이 실제 업로드 과정에서 강제되려면 서버가 최종적으로 업로드 허용 여부를 판단해야 한다고 생각했습니다.
  
#### 대소문자 처리

- 결정: 구현
- 적용 방향:
  - 커스텀 확장자 등록 시 소문자로 정규화
  - 파일 업로드 검증 시 추출한 확장자를 소문자로 정규화
  - DB에는 정규화된 값을 저장
  - `png`, `PNG`, `PnG`를 동일한 확장자로 처리
- 판단 이유:

  > 일반적인 파일 사용 환경에서는 대소문자만 다른 확장자를 서로 다른 파일 형식으로 구분하지 않는 경우가 많습니다. 대소문자를 구분하면 차단 정책이 예상과 다르게 동작하거나 동일한 확장자가 중복 등록될 수 있다고 생각했습니다.

#### 복합 확장자

- 결정: 구현
- 적용 방향:
  - `tar.gz`, `module.css`처럼 점으로 연결된 복합 확장자 등록 허용
  - 등록값을 파일명의 점 경계를 포함한 끝부분과 비교
  - `tar.gz` 등록 시 `backup.tar.gz` 차단, `backup.gz` 허용
  - `gz` 등록 시 `.gz`로 끝나는 모든 파일 차단
  - `*`, glob 패턴과 정규표현식 입력은 허용하지 않음
- 판단 이유:

  > `tar.gz`와 같은 복합 확장자도 실제로 자주 사용되기 때문에 이에 대한 명확한 차단 정책이 필요하다고 생각했습니다. 정규표현식이나 glob 패턴보다 복합 확장자 자체를 등록하도록 제한하는 방식이 사용자가 동작을 이해하기 쉽고, 입력 검증과 보안 복잡도도 줄일 수 있다고 판단했습니다.

예시:

| 등록 정책 | 파일명 | 결과 |
|---|---|---|
| `tar.gz` | `backup.tar.gz` | 차단 |
| `tar.gz` | `backup.gz` | 허용 |
| `gz` | `backup.tar.gz` | 차단 |
| `module.css` | `button.module.css` | 차단 |
| `css` | `button.module.css` | 차단 |

#### 확장자 없는 파일과 숨김 파일

- 결정: 구현
- 적용 방향:
  - 파일명에 점이 없거나 점으로 끝나면 확장자 없는 파일로 간주해 차단 대상에서 제외
  - 점으로 시작하는 파일은 예외를 두지 않고 복합 확장자와 동일한 접미사 일치 규칙을 파일명 전체에 적용
  - `env` 등록 시 `.env`는 차단, 점이 없는 `env`와 `README`, `Makefile`은 허용
  - `env` 등록 시 `.env.local`은 접미사가 일치하지 않아 허용, `env.local` 등록 시에만 `.env.local` 차단
- 판단 이유:

  > 확장자 없는 파일까지 별도의 차단 대상으로 추가하면 과제 범위를 넘어서는 UI와 데이터 모델이 필요합니다. 반면 `.env`와 같은 숨김 파일을 모두 확장자 없는 파일로 처리하면 사용자가 `env`를 등록했을 때 `.env`가 차단되지 않아 직관적인 기대와 어긋날 수 있다고 생각했습니다. 따라서 점 경계를 포함한 파일명 접미사 일치 원칙을 유지하면서, 확장자가 없는 파일은 허용하는 방향이 가장 일관적이라고 판단했습니다.

#### 업로드 파일명 길이 제한

- 결정: 구현
- 적용 방향:
  - 업로드 파일의 원본 파일명은 확장자를 포함해 최대 255바이트(UTF-8 기준)로 제한
  - 파일명 길이는 서버에서 최종 검증
  - 255바이트를 초과하면 저장과 ClamAV 검사 전에 업로드 거부
  - 클라이언트에서도 가능한 범위에서 사전 안내
  - 원본 파일명은 메타데이터로만 저장하며 실제 저장 파일명은 UUID v4 사용
  - 빈 파일명이나 파일명 길이 초과 시 명확한 오류 메시지 제공
  - 구체적인 문자 길이 계산 방식은 기술 설계 단계에서 확정(UTF-8 바이트 길이 기준으로 확정됨)
- 판단 이유:

  > 매우 긴 파일명은 확장자 정책과는 별개의 입력 안전성 문제라고 생각했습니다. 따라서 확장자 판정 로직에 포함하지 않고 별도의 파일명 길이 제한을 두는 방향으로 결정했습니다. 파일명 길이 제한은 데이터베이스나 프레임워크에 따라 정해지는 구현 방식이 아니라 사용자가 업로드할 수 있는 입력 범위를 정하는 정책이므로, 기술 설계 단계로 넘기지 않고 요구사항 단계에서 255바이트로 확정했습니다.

#### 입력값 정규화

- 결정: 구현
- 적용 방향:
  - 앞뒤 공백을 제거
  - 맨 앞의 마침표가 하나 있으면 제거(사용자 입력을 추론하지 않는 명시적인 형식 정규화 규칙)
  - 영문, 숫자와 복합 확장자 구분을 위한 내부 마침표만 허용
  - 하이픈, 언더스코어, 공백, 유니코드 문자를 포함한 그 외 문자는 입력 오류로 거부
  - 연속된 마침표 처리는 `연속된 마침표 처리` 항목에서 별도로 결정
- 판단 이유:

  > 앞뒤 공백과 맨 앞의 마침표는 사용자가 확장자를 입력할 때 흔히 포함할 수 있는 표현 차이이며, 이를 제거해도 등록하려는 확장자의 의미는 달라지지 않는다고 생각했습니다. 반면 하이픈, 언더스코어와 유니코드 문자까지 허용하면 검증 범위가 넓어지지만 현재 과제에서 얻는 실익은 크지 않습니다. 따라서 입력 형식을 영문, 숫자와 복합 확장자를 위한 내부 마침표로 제한하여 정책을 단순하고 예측 가능하게 유지하기로 판단했습니다.

예시:

| 입력 | 결과 |
|---|---|
| `.EXE` | `exe`로 저장 |
| `.env.local` | `env.local`로 저장 |
| `tar.gz` | `tar.gz`로 저장 |
| `my-ext` | 입력 오류 |
| `my_ext` | 입력 오류 |
| `한글확장자` | 입력 오류 |
| `⭐` | 입력 오류 |

#### 파일 시그니처 검증

- 결정: 구현
- 적용 방향:
  - 업로드 처리를 확장자 필터와 보안 필터 두 단계로 분리
  - 확장자 필터: 관리자가 설정한 차단 확장자 정책 검증, 대소문자 정규화, 단일 확장자와 복합 확장자 비교, 차단 정책에 일치하면 업로드 거부
  - 보안 필터: 확장자 정책과 별개로 ClamAV를 이용해 파일 자체의 악성 여부 검사, 악성 파일이 탐지되면 활성화된 확장자 정책과 관계없이 업로드 거부
  - 검사가 끝나기 전에는 파일을 최종 저장 위치에 저장하지 않음
  - ClamAV 검사 실패 또는 연결 실패 시 업로드를 허용하지 않음
  - `MZ`, `ELF`, Mach-O 같은 매직 넘버를 애플리케이션 코드에 직접 관리하지 않고, 특정 실행 파일 형식을 직접 판별해 차단하는 로직도 구현하지 않음
  - 모든 파일 형식을 완전히 판별하거나 파일 내부 코드의 의도를 분석하는 기능은 구현하지 않음
- 판단 이유:

  > 확장자 필터는 관리자가 설정한 차단 정책을 집행하는 기능이고, 악성 파일 검사는 업로드 자체의 안전성을 확인하는 기능이므로 두 역할을 분리해야 한다고 생각했습니다. 파일 시그니처를 직접 관리하면 제한된 형식만 검사하게 되고 지속적인 유지보수가 필요합니다. 따라서 악성 파일 검사는 해당 목적에 맞는 ClamAV에 위임하고, 확장자 필터와 보안 필터를 모두 통과한 파일만 저장하도록 구성하는 것이 적절하다고 판단했습니다.

예시:

| 상황 | 결과 |
|---|---|
| `exe` 차단 활성화 상태에서 `tool.exe` 업로드 | 확장자 필터에서 차단 |
| `exe` 차단 비활성화 상태에서 정상 `tool.exe` 업로드, ClamAV 미탐지 | 허용 |
| `photo.jpg`가 확장자 정책은 통과했지만 ClamAV에서 악성 파일로 탐지 | 보안 필터에서 차단 |
| 정상 파일이 확장자 필터와 보안 필터를 모두 통과 | 업로드 성공 |
| ClamAV 검사 자체를 수행할 수 없는 경우 | 업로드 거부 |

#### 업로드 파일 크기와 개수 제한

- 결정: 구현
- 적용 방향:
  - 한 번에 파일 하나만 업로드
  - 파일당 최대 크기를 관리 화면에서 설정할 수 있는 업로드 정책으로 관리하고, 확장자 정책과 구분된 영역에 배치
  - 설정 가능한 값은 `1MB`, `5MB`, `10MB`, `20MB`, `50MB`이며 기본값은 `10MB`
  - 설정값은 DB에 저장하고 새로고침 후에도 유지
  - 클라이언트와 서버가 동일한 저장값을 기준으로 파일 크기 검증
  - 서버와 배포 환경의 실제 요청 크기 상한을 초과하는 값은 설정할 수 없도록 제한
  - 크기 제한을 초과한 파일은 보안 검사와 최종 저장을 수행하지 않음
  - 다중 파일 업로드와 부분 성공 처리는 현재 범위에서 제외
  - 제한 초과 시 현재 설정된 최대 크기를 포함한 오류 메시지 표시
  - 관리 화면 UI는 슬라이더 단독이 아니라 선택형 입력 또는 숫자 입력과 슬라이더를 함께 사용하는 방식으로 구성
- 판단 이유:

  > 파일 크기를 하나의 고정값으로 정하면 서비스의 사용 목적이나 운영 환경이 달라질 때마다 코드를 수정해야 합니다. 확장자 차단과 마찬가지로 파일 크기도 관리자가 조정할 수 있는 업로드 정책으로 관리하는 것이 자연스럽다고 생각했습니다. 기본값 `10MB`는 일반적인 이미지와 문서 파일을 처리할 수 있으면서도 과도한 서버 자원 사용을 제한하기 위한 초기 운영값으로 설정했습니다. 다만 실제 허용 범위는 서버와 배포 환경의 제한을 넘지 않도록 구성하는 것이 적절하다고 판단했습니다.

예시:

| 상황 | 결과 |
|---|---|
| 최대 크기 `10MB` 설정 상태에서 `8MB` 파일 업로드 | 다음 검증 단계 진행 |
| 최대 크기 `10MB` 설정 상태에서 `12MB` 파일 업로드 | 크기 제한으로 거부 |
| 관리자가 최대 크기를 `20MB`로 변경 | 이후 업로드부터 변경된 정책 적용 |
| 여러 파일을 한 번에 전송 | 파일 개수 제한으로 거부 |
| 클라이언트 검증을 우회한 초과 파일 | 서버에서 거부 |

#### 원본 파일명 저장

- 결정: 구현
- 적용 방향:
  - 실제 저장 파일명은 `UUID v4` 기반으로 생성
  - 원본 파일명은 저장 경로나 실제 저장 파일명 생성에 사용하지 않음
  - 실제 저장 파일명에는 원본 확장자를 붙이지 않음
  - 원본 파일명, 정규화된 확장자, MIME 타입, 파일 크기, 저장 식별자, 업로드 시각을 DB 메타데이터로 저장
  - 저장 위치는 정적 파일 서빙 범위 밖의 고정된 디렉터리로 제한
  - 사용자가 전달한 경로나 파일명으로 저장 위치를 조합하지 않음
  - 동일한 원본 파일명이나 동일한 내용의 파일도 각각 독립된 업로드로 처리
  - 업로드마다 새로운 UUID를 생성하고 기존 파일을 덮어쓰지 않음
  - 파일 해시를 이용한 전역 중복 탐지와 기존 파일 존재 여부 안내는 구현하지 않음
  - 인증과 소유권이 없으므로 서버에 저장된 전체 파일 목록은 공개하지 않음
  - 업로드 성공 후 현재 화면에서 수행한 업로드 결과만 표시
  - 저장 실패 시 임시 파일과 불완전한 메타데이터가 남지 않도록 정리
- 판단 이유:

  > 원본 파일명을 실제 저장 경로에 사용하면 경로 조작, 파일명 충돌과 운영체제별 특수문자 처리 문제가 발생할 수 있습니다. 따라서 실제 저장 이름은 사용자 입력과 무관한 UUID로 생성하고 원본 파일명은 메타데이터로만 보존하는 것이 안전하다고 생각했습니다. 또한 현재는 인증과 파일 소유권 개념이 없으므로 같은 이름의 파일을 기존 파일에 덮어쓰거나 중복 파일의 존재 여부를 안내하면 다른 사용자의 파일에 영향을 주거나 저장 여부를 추론하게 할 수 있습니다. 따라서 모든 업로드를 독립된 항목으로 저장하고 전역 파일 목록은 공개하지 않는 것이 적절하다고 판단했습니다.

예시:

| 상황 | 결과 |
|---|---|
| 원본 `보고서.pdf` 업로드 | UUID 이름으로 저장하고 DB에는 원본명 기록 |
| 같은 이름의 `보고서.pdf` 재업로드 | 새로운 UUID로 별도 저장 |
| 동일한 내용의 `a.txt`, `b.txt` 업로드 | 각각 별도 저장 |
| 동일한 파일을 여러 번 재업로드 | 매번 새로운 UUID로 독립 저장, 기존 파일을 덮어쓰지 않음 |
| 서버 생성 파일명이 우연히 충돌하는 경우 | 새로운 UUID를 다시 생성해 저장 |
| 원본 파일명에 `../` 또는 경로 구분자 포함 | 저장 경로에는 반영하지 않음 |
| 업로드 성공 후 | 원본 파일명과 크기 등 결과만 현재 화면에 표시 |
| 실제 저장 UUID, 서버 경로, 파일 해시 | 사용자에게 노출하지 않음 |

#### MIME 타입 검증

- 결정: 구현
- 적용 방향:
  - 업로드 요청의 `Content-Type` 값을 클라이언트가 선언한 MIME 타입으로 저장
  - DB 필드명은 신뢰 가능한 탐지값으로 오해하지 않도록 `declaredMimeType` 또는 `clientMimeType` 사용
  - MIME 타입은 확장자 필터와 ClamAV 보안 필터의 차단 판단에 사용하지 않음
  - 확장자와 MIME 타입이 불일치하더라도 MIME 값만으로 업로드를 차단하거나 사용자에게 경고하지 않음
  - MIME 타입의 길이를 제한하고 제어문자 등 비정상적인 값은 저장하지 않음
  - 실제 파일 형식을 서버에서 탐지하는 기능이 추가되면 `detectedFileType`과 같은 별도 필드로 분리
  - 향후 다운로드 기능을 제공하더라도 저장된 클라이언트 MIME 타입을 그대로 응답의 `Content-Type`으로 신뢰하지 않음
  - 다운로드는 `application/octet-stream`, `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff` 방식으로 제공
  - MIME 타입은 장애 분석과 보안 로그의 참고 정보로만 활용
- 판단 이유:

  > 브라우저가 전달하는 MIME 타입은 클라이언트에서 조작할 수 있으므로 업로드 허용 여부를 결정하는 근거로 사용할 수 없습니다. 다만 업로드 요청 당시 클라이언트가 선언한 정보를 기록해두면 장애나 보안 문제를 분석할 때 참고 자료로 활용할 수 있다고 생각했습니다. 따라서 MIME 타입은 출처가 드러나는 메타데이터로만 저장하고, 확장자 필터와 ClamAV 보안 필터의 판단에는 영향을 주지 않도록 분리하는 것이 적절하다고 판단했습니다.

예시:

| 상황 | 결과 |
|---|---|
| `report.jpg`의 MIME 타입이 `image/jpeg`인 경우 | 메타데이터로만 저장 |
| `report.jpg`의 MIME 타입이 `application/x-msdownload`인 경우 | 해당 값만으로 차단하지 않음 |
| `malware.exe`의 MIME 타입이 `image/jpeg`로 조작된 경우 | 확장자 필터와 ClamAV 검증 결과로 판단 |
| MIME 타입이 없거나 `application/octet-stream`인 경우 | 다른 검증을 통과하면 업로드 허용 |
| 비정상적으로 긴 MIME 타입이나 제어문자가 포함된 값 | 저장하지 않음 |

### 정책과 데이터

#### 고정 확장자와 커스텀 확장자 중복

- 결정: 구현
- 적용 방향:
  - 커스텀 입력값 정규화 후 고정 확장자 목록과 대소문자 구분 없이 비교
  - 고정 확장자와 일치하면 커스텀 확장자로 저장하지 않음
  - 해당 고정 확장자가 비활성 상태라면 자동으로 활성화하고 DB에 저장
  - 해당 고정 확장자가 이미 활성 상태라면 상태를 변경하지 않음
  - 커스텀 확장자 개수에는 포함하지 않음
  - 처리 후 해당 고정 확장자가 활성화되었다는 안내 메시지 표시
  - 화면에서 자동 활성화된 고정 확장자 항목으로 포커스 또는 시각적 강조 이동
  - 고정 확장자 활성화 저장에 실패하면 화면 상태를 변경하지 않고 오류 안내
  - 커스텀 확장자 내부의 중복은 기존과 동일하게 등록 거부
- 판단 이유:

  > 사용자가 고정 확장자를 커스텀 입력창에 입력하는 경우는 해당 값이 고정 목록에 있다는 사실을 놓쳤거나, 그 확장자를 차단하려는 의도를 다른 입력 방식으로 표현한 상황일 수 있다고 생각했습니다. 단순히 오류로 거부하는 것보다 사용자의 차단 의도를 유지하면서 해당 고정 확장자를 활성화하는 방식이 더 자연스럽다고 판단했습니다. 다만 커스텀 확장자가 등록된 것으로 오해하지 않도록 자동 활성화 사실을 명확히 안내하고, 커스텀 목록과 개수 제한에는 포함하지 않도록 구분하기로 결정했습니다.

예시:

| 상황 | 결과 |
|---|---|
| 고정 `exe`가 비활성 상태에서 커스텀 입력창에 `exe` 입력 | 커스텀 등록 없이 고정 `exe` 자동 활성화 |
| 고정 `exe`가 이미 활성 상태에서 `EXE` 입력 | 추가 저장 없이 이미 차단 중이라는 안내 |
| 커스텀에 없는 `sh` 입력 | 일반 커스텀 확장자로 등록 |
| 자동 활성화된 `exe` | 커스텀 목록과 `200개` 제한에 포함하지 않음 |

#### 정책 변경 이력

- 결정: 구현(후순위 추가 작업)
- 적용 방향:
  - 현재 구현 범위에는 포함하지 않고, 필수 기능이 완료된 뒤 진행할 후순위 추가 작업으로 분리
  - 현재는 정책의 최신 상태만 저장
  - 후순위 작업에서는 조회 UI 없이 정책 변경 시 별도 로그 테이블에 변경 이력 저장
  - 기록 대상: 고정 확장자 활성화와 비활성화, 커스텀 확장자 추가와 삭제, 업로드 최대 크기 변경
  - 기록 항목: 정책 종류, 변경 대상, 변경 전 값, 변경 후 값, 변경 시각
  - 인증 기능이 없으므로 변경 주체는 기록하지 않음
  - 변경 이력은 `90일` 동안 보관하는 정책으로 정의하며, 실제 자동 삭제 기능은 후순위 추가 작업 범위에서 함께 검토
  - 뒤의 `로그와 모니터링` 항목에서는 정책 변경 로그를 다시 결정하지 않고 여기서 정한 내용을 참조하며, 업로드 성공과 실패, 차단 사유, ClamAV 오류, 저장 실패 등 나머지 운영 로그만 별도로 논의
- 판단 이유:

  > 정책 변경 이력은 문제 발생 시 과거 정책 상태를 추적하는 데 유용하다고 생각했습니다. 다만 현재 과제의 핵심은 확장자 정책이 실제 업로드에서 강제되는 기능을 완성하는 것이며, 정책 변경 이력은 필수 범위를 넘어서는 추가 기능입니다. 따라서 현재는 최신 정책 상태 저장에 집중하고, 변경 대상과 변경 전후 값, 변경 시각을 기록하는 기능은 핵심 기능 완료 후 진행할 추가 작업으로 분리하는 것이 적절하다고 판단했습니다. 인증 기능이 없어 변경 주체를 신뢰성 있게 식별할 수 없으므로 누가 변경했는지는 기록하지 않기로 결정했습니다.

#### 제한 초과 시 UX

- 결정: 구현
- 적용 방향:
  - 커스텀 확장자 입력 필드에 `maxlength=20` 적용
  - 현재 입력 글자 수를 `현재 글자 수/20` 형태로 표시
  - 20자를 초과하는 입력은 클라이언트에서 사전 차단
  - 커스텀 확장자 개수를 `현재 개수/200` 형태로 항상 표시
  - 200개에 도달하면 `추가` 버튼만 비활성화
  - 입력창은 유지하고 `최대 200개까지 등록할 수 있습니다. 기존 항목을 삭제한 후 다시 추가해주세요.` 안내 표시
  - 기존 항목을 삭제해 199개 이하가 되면 `추가` 버튼 다시 활성화
  - Enter 키 제출도 동일한 조건으로 제한
  - 제한 초과 오류가 발생해도 현재 입력값은 유지
  - 글자 수와 개수 안내는 색상에만 의존하지 않고 텍스트로 제공
  - 서버는 클라이언트 상태와 관계없이 다음을 최종 검증
    - 정규화된 확장자 길이가 20자 이하인지 검증
    - 현재 커스텀 확장자 개수가 200개 미만인지 검증
    - 동일한 커스텀 확장자가 이미 등록되어 있는지 검증
    - 고정 확장자와 겹치는 값인지 검증하고, 앞서 정한 고정 확장자 활성화 정책 적용
    - 직접 API를 호출하거나 요청을 변조해도 제한을 초과한 값은 저장하지 않음
    - 동시 요청으로 200개를 초과하지 않도록 DB 제약과 트랜잭션 수준에서 처리
    - 서버 검증 실패 시 DB를 변경하지 않고 명확한 오류 코드와 메시지 반환
    - 서버 응답을 기준으로 화면의 개수와 목록을 최신 상태로 다시 반영
- 판단 이유:

  > 제한을 초과한 뒤 오류를 보여주는 것보다 사용자가 현재 한도를 미리 확인하고 잘못된 요청을 보내지 않도록 하는 것이 더 자연스럽다고 생각했습니다. 글자 수 제한은 입력 단계에서 바로 막아도 사용자의 다음 행동이 명확하지만, 최대 개수에 도달했을 때 입력창까지 비활성화하면 기존 항목을 삭제해야 한다는 사실을 이해하기 어려울 수 있습니다. 따라서 입력창은 유지하고 추가 동작만 제한하면서, 기존 항목을 삭제한 뒤 다시 시도해야 한다는 안내를 제공하는 방식이 적절하다고 판단했습니다. 또한 클라이언트 검증은 우회할 수 있으므로 길이, 개수, 중복과 고정 확장자 중복 여부는 서버에서 최종적으로 다시 검증하기로 결정했습니다.

예시:

| 상황 | 결과 |
|---|---|
| 20자 입력 상태에서 추가 문자 입력 | 클라이언트에서 더 이상 입력되지 않음 |
| 변조된 요청으로 21자 값을 전송 | 서버에서 거부 |
| 200개 등록 상태 | 입력창 유지, 추가 버튼 비활성화, 기존 항목 삭제 안내 |
| 200개 상태에서 직접 API 호출 | 서버에서 거부 |
| 두 요청이 동시에 200번째 항목을 추가하려는 경우 | 하나만 성공하고 나머지는 서버에서 거부 |
| 항목 하나를 삭제해 199개가 된 경우 | 최신 목록 반영 후 추가 버튼 다시 활성화 |

#### 확장자 인덱스

- 결정: 구현
- 적용 방향:
  - 정규화된 커스텀 확장자 컬럼에 `UNIQUE` 제약 적용
  - 대소문자 변환과 선행 점 제거 등 정규화가 완료된 값만 저장
  - 애플리케이션에서 먼저 중복 여부를 확인해 사용자에게 명확한 오류 메시지 제공
  - 동시에 같은 확장자를 등록하는 요청이 들어오더라도 DB 제약으로 하나만 저장
  - `UNIQUE` 제약으로 생성되는 인덱스를 중복 조회에 활용
  - 커스텀 확장자는 최대 200개로 제한되므로 별도의 추가 조회 성능 인덱스는 적용하지 않음
  - 고정 확장자와 커스텀 확장자의 중복은 테이블 간 정책이므로 서버 로직에서 처리
  - 최대 200개 제한은 `UNIQUE` 제약과 별개의 문제로 보고 서버 트랜잭션에서 처리
  - DB 제약 위반 시 중복 등록 오류로 변환해 사용자에게 안내
- 판단 이유:

  > 커스텀 확장자는 정규화된 값을 기준으로 중복 여부를 판단하므로, 데이터베이스에도 동일한 기준의 `UNIQUE` 제약을 적용하는 것이 일관적이라고 생각했습니다. 애플리케이션에서 먼저 중복을 확인하면 사용자에게 친절한 메시지를 제공할 수 있지만, 동시에 같은 값이 등록되는 상황까지 완전히 방지할 수는 없습니다. 따라서 최종 데이터 무결성은 데이터베이스 제약으로 보장하고, 데이터 규모가 최대 200개로 작기 때문에 별도의 추가 인덱스는 두지 않는 것이 적절하다고 판단했습니다.

예시:

| 상황 | 결과 |
|---|---|
| `sh`가 없는 상태에서 등록 요청 | 정상 저장 |
| `sh`가 이미 있는 상태에서 다시 등록 | 서버에서 중복 오류 반환 |
| `SH`와 `sh`가 동시에 요청됨 | 정규화 후 하나만 저장 |
| 서로 다른 확장자가 동시에 요청됨 | `UNIQUE` 제약과 무관하게 각각 처리 |
| 고정 확장자인 `exe` 입력 | 커스텀 테이블에 저장하지 않고 앞서 정한 고정 확장자 활성화 정책 적용 |

### UX와 예외

#### 차단 메시지

- 결정: 구현
- 적용 방향:
  - 차단된 파일명과 확장자를 표시합니다
  - 현재 차단 정책에 따라 업로드가 거부되었음을 안내합니다
  - 사용자가 실패 원인을 바로 확인할 수 있는 위치에 메시지를 표시합니다
- 판단 이유:

  > 파일 업로드가 실패했다는 결과만 보여주면 사용자가 원인을 알기 어렵습니다. 어떤 파일이 어떤 확장자 정책에 의해 차단되었는지 명확하게 안내해야 다음 행동을 결정할 수 있다고 생각했습니다.

#### 저장 실패 처리

- 결정: 구현
- 적용 방향:
  - 고정 확장자 체크
    - 사용자의 체크 상태를 화면에 즉시 반영
    - 짧은 Debounce 이후 최종 상태를 서버에 저장
    - 연속된 변경은 마지막 상태만 저장
    - 저장 중임을 사용자에게 표시
    - 저장 실패 시 서버의 최신 정책을 다시 조회해 화면 상태 동기화
    - 저장 실패 사실과 변경 내용이 반영되지 않았음을 안내
    - 저장 대기 중 새로고침이나 페이지 이동이 발생할 경우 미저장 변경이 유실되지 않도록 처리
  - 커스텀 확장자 추가
    - 추가 버튼 클릭 직후 로딩 인디케이터와 `추가 중...` 상태 표시
    - 서버 저장에 성공한 뒤 목록에 추가
    - 요청 중 추가 버튼 비활성화로 중복 제출 방지
    - 성공 전까지 입력값 유지
    - 성공 시 목록 반영 후 입력값 초기화
    - 실패 시 목록을 변경하지 않고 입력값 유지
    - 실패 사유를 안내하고 재시도 가능하게 처리
    - 버튼 문구 변경으로 레이아웃이 움직이지 않도록 크기 유지
  - 커스텀 확장자 삭제
    - 삭제 요청 직후 해당 삭제 버튼에 로딩 상태 표시
    - 서버 삭제에 성공한 뒤 목록에서 제거
    - 요청 중 해당 항목의 삭제 버튼만 비활성화
    - 삭제 실패 시 기존 항목 유지
    - 실패 사유를 안내하고 재시도 가능하게 처리
  - 모든 변경은 서버에서 최종 검증
  - 서버 응답이나 재조회 결과를 기준으로 화면 상태 동기화
  - 화면 전체를 차단하지 않고 변경 중인 요소만 로딩 상태로 처리
  - 처리 상태와 오류 메시지는 색상에만 의존하지 않고 텍스트로 제공
  - 비동기 상태 변경은 스크린 리더가 인식할 수 있도록 전달
- 판단 이유:

  > 고정 확장자 체크는 사용자가 여러 항목을 연속해서 변경할 수 있으므로 화면에 즉시 반영하고, 일정 시간 동안의 변경을 모아 최종 상태만 저장하는 방식이 빠른 조작 경험과 요청 감소에 적절하다고 생각했습니다. 저장에 실패하면 서버의 최신 상태를 다시 조회해 화면과 DB를 일치시키도록 구성했습니다. 반면 커스텀 확장자의 추가와 삭제는 각 작업의 성공 여부가 목록 구성에 직접 영향을 주므로 서버 저장이 완료된 뒤에만 화면에 반영하는 것이 적절하다고 판단했습니다. 서버 응답을 기다리는 동안에는 변경 대상에 즉시 로딩 상태를 표시해 사용자의 입력에 대한 반응성을 제공하고 중복 요청을 방지하기로 결정했습니다.

예시:

| 상황 | 결과 |
|---|---|
| `exe` 체크 | 화면 즉시 체크, Debounce 이후 저장 성공 시 유지 |
| `exe` 체크 후 빠르게 해제 | 최종 해제 상태만 저장 |
| 고정 확장자 저장 실패 | 서버 상태 재조회 후 실제 저장 상태로 복구 |
| 커스텀 `sh` 추가 클릭 | 버튼에 `추가 중...` 표시, 저장 성공 후 목록 반영과 입력값 초기화 |
| 커스텀 `sh` 추가 실패 | 목록과 입력값 유지, 오류 안내 |
| 커스텀 항목 삭제 클릭 | 해당 삭제 버튼 로딩, 성공 후 목록에서 제거 |
| 커스텀 항목 삭제 실패 | 목록에 그대로 유지, 오류 안내 |

#### 네트워크 오류 처리

- 결정: 구현
- 적용 방향:
  - 브라우저가 오프라인 상태인 경우 인터넷 연결 확인 안내
  - 요청이 타임아웃되거나 응답을 받지 못한 경우 네트워크 상태 확인 후 재시도 안내
  - 서버가 `4xx` 응답을 반환한 경우 서버가 전달한 검증 오류 메시지 표시
  - 서버가 `5xx` 응답을 반환한 경우 일시적인 서버 오류 안내
  - 오류 발생 시 변경 중이던 버튼과 입력 요소를 다시 활성화
  - 자동 재시도는 적용하지 않고 사용자가 직접 재시도
  - 커스텀 확장자 추가 실패 시 입력값 유지
  - 커스텀 확장자 삭제 실패 시 기존 항목 유지
  - 고정 확장자 저장 실패 시 서버 상태를 다시 조회해 화면 동기화
  - 오류 메시지는 색상에만 의존하지 않고 텍스트로 제공
  - 동일한 오류가 중복으로 쌓이지 않도록 현재 작업 단위로 표시
- 판단 이유:

  > 네트워크 연결 문제와 서버가 반환한 오류는 사용자가 취할 수 있는 대응 방법이 다르므로, 클라이언트에서 확인 가능한 범위 안에서 구분해 안내하는 것이 적절하다고 생각했습니다. 다만 자동 재시도를 적용하면 요청의 성공 여부를 사용자가 파악하기 어려워지고 중복 변경 가능성도 생길 수 있으므로, 오류 원인을 안내한 뒤 사용자가 직접 재시도하는 방식을 선택했습니다. 이를 통해 저장 실패 처리에서 정한 화면 상태 유지 원칙을 지키면서도 사용자가 다음 행동을 판단할 수 있도록 구성하는 것이 적절하다고 판단했습니다.

예시:

| 상황 | 결과 |
|---|---|
| 브라우저 오프라인 상태에서 요청 | `인터넷 연결을 확인한 후 다시 시도해주세요.` |
| 요청 타임아웃 또는 응답 없음 | `서버에 연결하지 못했습니다. 잠시 후 다시 시도해주세요.` |
| 서버 검증 실패 | `이미 등록된 확장자입니다.` 등 구체적인 사유 표시 |
| 서버 내부 오류 | `일시적인 오류가 발생했습니다. 다시 시도해주세요.` |
| 오류 발생 후 | 로딩 상태 해제, 사용자가 동일 작업을 다시 실행할 수 있도록 처리 |

#### 접근성

- 결정: 구현
- 적용 방향:
  - 체크박스와 입력 필드에 `label`을 명시적으로 연결
  - 체크, 추가, 삭제, 업로드 기능을 `button`, `input` 등 의미에 맞는 시맨틱 요소로 구현
  - 모든 기능을 키보드만으로 조작 가능하게 처리
  - Tab 이동 순서를 DOM 순서와 자연스럽게 일치
  - 양수 `tabindex`는 사용하지 않음
  - 키보드 포커스를 확인할 수 있도록 `:focus-visible` 스타일 제공
  - 검증 실패 시 문제가 발생한 입력 필드로 포커스 이동
  - 업로드가 차단된 경우 파일 입력 또는 오류 안내 영역으로 포커스 이동
  - 커스텀 확장자 삭제 후 포커스가 사라지지 않도록 다음 항목의 삭제 버튼이나 입력 필드로 이동
  - 단순 저장 성공이나 로딩 완료 시에는 포커스를 강제로 이동하지 않음
  - 아이콘만 있는 삭제 버튼에 접근 가능한 이름 제공
  - 앞서 결정한 색상 비의존 안내와 스크린 리더 상태 전달 원칙을 화면 전체에 적용
  - 동적 상태 전달은 필요한 영역에만 `aria-live`를 적용
  - 네이티브 HTML로 해결 가능한 요소에는 불필요한 ARIA를 추가하지 않음
  - 별도 접근성 라이브러리나 전체 WCAG AA 인증 절차는 적용하지 않음
- 판단 이유:

  > 이번 과제에서 접근성 자체가 핵심 기능은 아니지만, 레이블 연결, 키보드 조작, 포커스 표시와 같이 기본적으로 지켜야 하는 접근성은 구현해야 한다고 생각했습니다. WCAG AA 전체 준수나 별도의 인증과 실기기 검증까지 진행하는 것은 과제 범위에 비해 과하므로 제외했습니다. 대신 시맨틱 HTML을 우선 사용하고, 오류나 삭제처럼 사용 흐름이 끊길 수 있는 상황에만 의도적으로 포커스를 이동하는 방식이 적절하다고 판단했습니다.

예시:

| 상황 | 결과 |
|---|---|
| 커스텀 확장자 입력 오류 | 오류 메시지 표시 후 해당 입력 필드로 포커스 이동 |
| 커스텀 항목 삭제 | 다음 삭제 버튼으로 이동, 다음 항목이 없으면 입력 필드로 이동 |
| 고정 확장자 체크 | 현재 체크박스에 포커스 유지 |
| 커스텀 확장자 추가 성공 | 포커스 강제 이동 없이 입력 필드에서 계속 입력 가능 |
| 업로드 차단 | 차단 사유를 전달하고 파일 입력 또는 오류 안내 영역으로 포커스 이동 |
| 로딩, 저장 실패, 네트워크 오류 | 텍스트와 스크린 리더 전달을 함께 제공 |

#### 반응형

- 결정: 구현
- 적용 방향:
  - 전체 콘텐츠 영역은 뷰포트 너비에 맞게 유동적으로 축소
  - 고정 확장자 목록은 `flex-wrap`을 사용해 공간이 부족하면 자연스럽게 다음 줄로 이동
  - 커스텀 확장자 목록도 동일하게 자동 줄바꿈
  - 입력 필드는 남은 공간을 유동적으로 사용
  - 입력 필드와 추가 버튼은 공간이 부족하면 자연스럽게 다음 줄로 이동
  - 파일 입력과 업로드 요소도 고정 너비에 의존하지 않도록 구성
  - 긴 확장자 값이 부모 영역을 벗어나지 않도록 처리
  - 가로 스크롤 없이 주요 기능을 사용할 수 있도록 구성
  - 세부 화면 크기별 전용 레이아웃과 다수의 미디어 쿼리는 적용하지 않음
  - 극단적으로 좁은 화면에서 필요한 최소한의 보정만 적용
- 판단 이유:

  > 이번 프로젝트는 화면 구조가 복잡하지 않아 화면 크기별로 별도의 레이아웃을 설계할 필요는 없다고 생각했습니다. 특정 브레이크포인트에서 배치를 강제로 전환하기보다, 사용 가능한 공간에 따라 요소가 자연스럽게 줄어들고 `flex-wrap`으로 다음 줄에 배치되는 방식이 더 유연한 사용자 경험을 제공한다고 판단했습니다. 따라서 기본적인 유동 레이아웃만 적용하고, 다수의 미디어 쿼리와 화면 크기별 맞춤 구성은 제외하기로 결정했습니다.

예시:

| 상황 | 결과 |
|---|---|
| 넓은 화면 | 입력 필드와 추가 버튼이 한 줄에 배치 |
| 공간이 부족한 화면 | 요소가 자연스럽게 다음 줄로 이동 |
| 고정 확장자와 커스텀 확장자가 많아짐 | 목록이 여러 줄로 자동 배치 |
| 긴 복합 확장자 표시 | 부모 영역 안에서 줄바꿈되거나 크기가 제한됨 |
| 작은 화면 | 가로 스크롤 없이 추가, 삭제, 업로드 가능 |

### 운영과 확장

#### 동시 편집 정합성

- 결정: 구현
- 적용 방향:
  - 별도의 버전 컬럼, 낙관적 잠금, 실시간 동기화는 적용하지 않음
  - 고정 확장자는 변경된 확장자의 활성화 상태만 서버에 전달
  - 커스텀 확장자는 추가와 삭제를 각각 독립된 요청으로 처리
  - 업로드 크기 정책은 마지막으로 저장된 값을 최신 값으로 사용
  - 모든 요청은 서버의 현재 데이터를 기준으로 검증
  - 중복 추가는 `UNIQUE` 제약으로 방지
  - 이미 삭제된 항목을 다시 삭제하는 요청은 현재 상태를 기준으로 처리
  - 저장 성공 시 서버 응답을 기준으로 변경된 화면 상태 갱신
  - 새로고침 시 전체 정책을 서버에서 다시 조회
  - 저장 실패 시 앞서 결정한 방식대로 서버 상태를 재조회해 동기화
  - 다른 탭의 변경을 자동으로 실시간 반영하지 않음
  - 오래 열린 화면에서는 새로고침 전까지 다른 탭의 변경이 보이지 않을 수 있음을 허용
- 판단 이유:

  > 이번 프로젝트는 인증과 사용자별 소유권이 없는 단일 정책 관리 화면이며, 여러 사용자가 동시에 편집하는 협업 환경을 주요 사용 사례로 보기는 어렵다고 생각했습니다. 따라서 버전 비교나 실시간 동기화를 추가하는 것은 과제 범위에 비해 구현 비용이 크다고 판단했습니다. 다만 전체 정책을 한 번에 덮어쓰면 서로 다른 항목의 변경까지 유실될 수 있으므로, 고정 확장자 변경과 커스텀 확장자 추가 및 삭제를 각각 독립적인 요청으로 처리해 충돌 범위를 줄이기로 결정했습니다.

예시:

| 상황 | 결과 |
|---|---|
| 한 탭에서 `exe` 활성화, 다른 탭에서 `js` 활성화 | 각 확장자 변경을 독립적으로 저장 |
| 두 탭에서 동시에 `sh` 추가 | 하나만 저장되고 나머지는 중복 오류 |
| 한 탭에서 항목 삭제 후 다른 탭에서 같은 항목 삭제 | 서버의 현재 상태를 기준으로 이미 삭제된 항목으로 처리 |
| 두 탭에서 업로드 크기를 각각 변경 | 마지막으로 정상 저장된 값 적용 |
| 다른 탭에서 변경된 정책 | 현재 화면에는 자동 반영하지 않고 새로고침 시 최신 상태 조회 |

#### 로그와 모니터링

- 결정: 구현
- 적용 방향:
  - 업로드 요청마다 고유 요청 ID 부여
  - 업로드 성공 또는 실패 결과 기록
  - 실패 사유는 정해진 유형으로 구분
    - 업로드 요청 형식 오류(파일 누락, 다중 파일 전송, 잘못된 multipart 형식)
    - 요청 크기 초과(서버 절대 상한 초과)
    - 파일명 형식 오류(빈 파일명, 길이 초과)
    - 확장자 정책 차단
    - 파일 크기 초과(정책상 최대 크기 초과)
    - ClamAV 악성 파일 탐지
    - ClamAV 연결 또는 검사 실패
    - 저장소 저장 실패
    - 메타데이터 저장 실패
    - 서버 내부 오류
  - 업로드 요청 형식 오류는 로그에서 공통 유형 `INVALID_UPLOAD_REQUEST`로 기록하고, 세부 코드로 `FILE_REQUIRED`(파일 누락), `MULTIPLE_FILES_NOT_ALLOWED`(다중 파일 전송), `INVALID_MULTIPART_REQUEST`(잘못된 multipart 형식)를 구분
  - 요청 크기 초과는 로그에서 `REQUEST_TOO_LARGE`로 기록하며, 파싱된 파일 자체가 정책상 최대 크기를 초과한 `파일 크기 초과`(`FILE_SIZE_EXCEEDED`)와는 별개 유형
  - 파일명 형식 오류는 로그에서 공통 유형 `INVALID_FILENAME`으로 기록하고, 세부 코드로 `EMPTY_FILENAME`(빈 파일명)과 `FILENAME_TOO_LONG`(길이 초과)을 구분
  - 사용자 화면에는 빈 파일명과 파일명 길이 초과를 각각 구체적인 사유로 구분해 표시
  - 업로드 요청 형식 오류는 정상적인 화면 흐름에서는 발생 가능성이 낮은 방어적 오류로, 직접 API를 호출하거나 요청을 변조하는 경우에 대비
  - 요청 크기 초과는 성격이 달라 정상적인 화면 업로드에서도 발생할 수 있음(정책상 허용된 크기에 가까운 파일을 선택한 경우 multipart 오버헤드나 서버 절대 상한에 따라 거부될 수 있음)
  - 요청 시각과 처리 시간 기록
  - 파일 크기와 정규화된 확장자 기록
  - ClamAV 검사 결과와 저장소 저장 결과 기록
  - 원본 파일 내용, 저장 경로, 저장 식별자 등 불필요한 민감 정보는 로그에 기록하지 않음
  - 오류 객체 전체를 그대로 노출하지 않고 운영에 필요한 오류 코드와 요약 정보만 기록
  - 사용자에게 표시하는 오류 메시지와 내부 로그를 분리
  - 별도의 로그 조회 UI와 통계 대시보드는 구현하지 않음
  - 정책 변경 로그와 업로드 운영 로그는 목적이 다르므로 분리해서 관리
  - 로그 보관 기간과 삭제 방식은 실제 배포 환경을 확정한 뒤 기술 설계에서 결정
- 판단 이유:

  > 업로드 과정에는 확장자 차단, 파일 크기 초과, ClamAV 검사 실패, 저장소 저장 실패 등 여러 실패 지점이 있으므로 문제가 반복될 때 원인을 확인할 수 있는 최소한의 기록은 필요하다고 생각했습니다. 다만 별도의 조회 화면과 모니터링 대시보드를 구현하는 것은 과제 범위에 비해 우선순위가 낮으므로 제외했습니다. 요청 결과와 실패 유형을 구조화된 형태로 기록하되, 파일 내용이나 저장 경로처럼 원인 분석에 필요하지 않은 정보는 남기지 않는 것이 적절하다고 판단했습니다.
  >
  > 파일명 검증 실패는 확장자 정책 차단이나 서버 내부 오류와 원인이 명확히 다르다고 생각했습니다. 실제 검증 단계와 화면에 표시되는 실패 사유를 로그에서도 구분해야 운영 중 원인을 정확히 파악할 수 있으므로, `INVALID_FILENAME`을 별도 실패 유형으로 추가하는 것이 적절하다고 판단했습니다.
  >
  > 실패 사유 목록은 파일 객체가 정상적으로 전달됐다는 전제에서 시작하지만, 직접 API를 호출하거나 요청을 변조하면 파일 누락, 다중 파일 전송, 잘못된 multipart 형식처럼 파일 객체 자체가 성립하지 않는 요청도 들어올 수 있다고 생각했습니다. 한 번에 파일 하나만 업로드한다는 요구사항도 서버가 최종적으로 검증해야 하므로, 이런 요청 형식 오류를 `INVALID_UPLOAD_REQUEST`라는 별도 실패 유형으로 구분해 기록하는 것이 적절하다고 판단했습니다.
  >
  > 서버가 요청을 받아들이는 절대 상한과, 관리자가 설정한 업로드 최대 크기 정책은 성격이 다르다고 생각했습니다. 전자는 정책값과 무관하게 서버 자원을 보호하기 위한 고정 상한이고, 후자는 사용자가 화면에서 바꿀 수 있는 값입니다. 두 실패를 같은 유형으로 묶으면 원인 분석 시 요청 자체가 과도하게 컸는지, 현재 정책보다 파일이 컸는지 구분할 수 없으므로 `REQUEST_TOO_LARGE`를 `FILE_SIZE_EXCEEDED`와 분리된 실패 유형으로 추가하는 것이 적절하다고 판단했습니다.

예시:

```text

reason: BLOCKED_EXTENSION
extension: exe
fileSize: 1048576
durationMs: 42
createdAt: ...
```




## 3. 추가 고려사항

과제 원문에 없지만 직접 발견한 요구사항과 판단을 기록합니다.

### 빈 입력 처리

- 결정: 구현
- 적용 방향:
  - 커스텀 확장자 입력값을 정규화한 결과가 빈 문자열이면 `추가` 버튼 비활성화
  - 빈 문자열뿐 아니라 공백만 입력한 경우도 동일하게 처리
  - Enter 키 제출도 동일한 조건으로 차단
  - 입력값이 유효해지면 `추가` 버튼 활성화
  - 서버에서도 정규화 후 빈 문자열인지 최종 검증
  - 직접 API를 호출하거나 요청을 변조해도 빈 값은 저장하지 않음
  - 버튼 비활성화 상태만으로 의미를 전달하지 않고 입력 필드의 레이블이나 안내 문구로 입력이 필요함을 명확히 제공
  - 빈 입력은 오류 메시지를 발생시키기보다 제출 자체를 막는 방식으로 처리
- 판단 이유:

  > 빈 입력은 서버에서 처리해야 할 유효한 요청이 아니므로 사용자가 제출한 뒤 오류를 확인하게 하기보다 입력 단계에서 추가 동작을 제한하는 것이 자연스럽다고 생각했습니다. 앞뒤 공백을 제거한 결과가 빈 문자열인 경우도 동일하게 처리하고, 클라이언트 검증은 우회할 수 있으므로 서버에서도 다시 검증하기로 결정했습니다.

예시:

| 상황 | 결과 |
|---|---|
| 빈 입력 상태 | `추가` 버튼 비활성화 |
| 공백만 입력 | 정규화 후 빈 문자열로 판단, `추가` 버튼 비활성화 |
| 유효한 확장자 입력 | `추가` 버튼 활성화 |
| 변조된 요청으로 빈 문자열 전송 | 서버에서 거부 |
| 입력값을 모두 지움 | 다시 `추가` 버튼 비활성화 |

### 연속된 마침표 처리

- 결정: 구현
- 적용 방향:
  - 정규화된 입력값에 연속된 마침표 `..`가 포함되어 있으면 등록 거부
  - 연속된 마침표를 하나로 자동 변환하지 않음
  - 오류 발생 시 입력값 유지
  - `연속된 마침표는 사용할 수 없습니다.` 안내 표시
  - 클라이언트에서 사전 검증
  - 서버에서도 동일한 규칙으로 최종 검증
  - 직접 API를 호출하거나 요청을 변조해도 저장하지 않음
  - 선행 마침표 하나를 제거한 뒤 연속된 마침표 여부 검증
  - 마침표로 시작하거나 끝나는 정규화 결과도 허용하지 않음
  - 각 구간은 영문자와 숫자를 하나 이상 포함하도록 검증
- 판단 이유:

  > 연속된 마침표는 단순한 표기 차이가 아니라 사용자가 의도한 확장자를 명확히 판단하기 어려운 입력이라고 생각했습니다. 이를 자동으로 하나의 마침표로 변환하면 사용자가 입력한 값과 실제 저장된 값이 달라질 수 있으므로, 명확한 오류로 안내하고 수정하도록 하는 것이 적절하다고 판단했습니다.

예시:

| 상황 | 결과 |
|---|---|
| `tar.gz` | 정상 등록 |
| `.tar.gz` | 선행 마침표 제거 후 `tar.gz`로 정상 등록 |
| `tar..gz` | 등록 거부 |
| `tar...gz` | 등록 거부 |
| `tar.` | 등록 거부 |
| `.tar.` | 정규화 후 `tar.`이므로 등록 거부 |
| 변조된 요청으로 `tar..gz` 전송 | 서버에서 거부 |

### 업로드 중 정책 변경

- 결정: 구현
- 적용 방향:
  - 서버가 파일을 실제로 검증하는 시점에 최신 정책을 조회
  - 클라이언트가 알고 있는 정책 상태를 신뢰하지 않음
  - 업로드 요청 시작 시점의 정책을 별도로 저장하거나 고정하지 않음
  - 정책 버전과 정책 스냅샷은 사용하지 않음
  - 최신 확장자 차단 정책과 업로드 크기 정책을 기준으로 검증
  - 정책 검증을 통과한 뒤 ClamAV 검사와 저장소 저장 진행
  - 검증 도중 정책이 다시 변경되더라도 이미 조회한 정책을 기준으로 해당 요청 처리
  - 다음 업로드 요청부터 변경된 최신 정책 적용
  - 정책 변경으로 업로드가 거부된 경우 현재 적용된 차단 사유를 명확히 안내
- 판단 이유:

  > 업로드 정책은 서버에서 실제 검증이 이루어지는 시점의 최신 상태를 기준으로 적용하는 것이 일관적이라고 생각했습니다. 요청 시작 시점의 정책을 고정하려면 별도의 정책 버전과 스냅샷 관리가 필요해 현재 과제 범위에 비해 복잡도가 커집니다. 따라서 서버가 검증을 시작할 때 최신 정책을 조회하고, 해당 요청은 조회한 정책을 기준으로 끝까지 처리하는 방식이 적절하다고 판단했습니다.

예시:

| 상황 | 결과 |
|---|---|
| 업로드 시작 후 검증 전에 `exe`가 차단됨 | 최신 정책에 따라 업로드 거부 |
| 업로드 시작 후 검증 전에 `exe` 차단이 해제됨 | 최신 정책에 따라 업로드 허용 |
| 서버가 정책을 조회한 뒤 검사 중 정책이 변경됨 | 해당 요청은 조회 당시 정책으로 계속 처리 |
| 다음 업로드 요청 | 변경된 최신 정책 적용 |

- [ ] 선택 상태가 DB에 저장됩니다
